## Purpose

Defines document categories to clarify terminology in sponsor communication and establish clear boundaries between framework operations, application specifications, and deliverables.

## Scope

All documents created within ROME projects. Used for sponsor interaction, robot coordination, and artifact organization.

---

## Document Categories

### 1. Framework Documents
**Location:** `/ROME/`
**Audience:** Framework developers, architects
**Examples:** `core-principles.md`, `activity-logging-protocol.md`, robot definitions
**Sponsor Visibility:** None (internal framework governance)

---

### 2. User Input
**Location:** `/_user_input/raw-requirements/`
**Audience:** Sponsor → Robots
**Examples:** PRDs, BRDs, requirements documents, reference materials
**Sponsor Interaction:** Sponsor provides these at project start

---

### 3. Application Specifications
**Location:** `/ARTIFACTS/[phase]/`
**Audience:** Sponsor review, robot implementation
**Purpose:** Blueprint defining WHAT the application does

| Document | Phase | Description |
|----------|-------|-------------|
| `requirements-matrix.yaml` | P2 | Structured requirements across 8 dimensions |
| `user-stories.md` | P2 | User stories with acceptance criteria |
| `data-dictionary.yaml` | P3 | **Single source of truth** for all entities, fields, relationships |
| `data-model.md` | P3 | Entity-relationship diagrams and explanations |
| `api-design.md` | P3 | API endpoints, request/response formats |
| `system-architecture.md` | P3 | System components, layers, interactions |
| `tech-stack.md` | P3 | Technology choices with justifications |
| `use-cases.md` | P3 | Detailed user workflows |

**Sponsor Interaction:** Review and approve at phase gates

---

### 4. Working Documents
**Location:** `/ARTIFACTS/[phase]/`
**Audience:** Robot coordination, audit trail
**Purpose:** Process artifacts generated during development

| Document | Phase | Description |
|----------|-------|-------------|
| `document-catalog.md` | P1 | Inventory of ingested sponsor materials |
| `ingest-summary.md` | P1 | Summary of P1 intake process |
| `phase2-handover.md` | P2 | Talib → PMA handover |
| `phase3-handover.md` | P3 | PMA → Lucien handover |
| `phase4-handover.md` | P4 | Lucien → P5 robots handover |
| `technical-specs.md` | P4 | Implementation specs per workspace |
| `scaffolding-manifest.md` | P4 | Record of what was scaffolded |
| `actionlist.md` | P3 | Feature breakdown, robot assignments |

**Sponsor Interaction:** Summaries in progress updates, not detailed review

---

### 5. Application Configuration
**Location:** `/SOURCE/[workspace]/`
**Audience:** Developers, CI/CD systems
**Purpose:** Files that configure, build, and run the application

| Type | Examples |
|------|----------|
| Project files | `package.json`, `pubspec.yaml`, `requirements.txt` |
| Build config | `tsconfig.json`, `webpack.config.js` |
| Environment | `.env.example`, `.env.development` |
| CI/CD | `.github/workflows/ci.yml` |
| Linting | `.eslintrc`, `.prettierrc` |

**Sponsor Interaction:** None (technical implementation detail)

---

### 6. Implementation Code
**Location:** `/SOURCE/[workspace]/`
**Audience:** Developers, generated by P5 robots
**Purpose:** Executable application code

Capabilities are project-specific and declared in tech-stack.yaml (P3); the rows below are illustrative, not fixed. Producer roles are assigned per project.

| Capability (example) | Role (example) | Examples |
|----------------------|----------------|----------|
| database | Ashok | Migrations, models, seeds, database tests |
| api | Reena | Controllers, services, routes, API tests |
| ui-app | Charlie | Components, screens, state management, UI tests |

**Sponsor Interaction:** Demos of working application, not code review

---

### 7. Test Artifacts
**Location:** `/SOURCE/[workspace]/tests/`, `/ARTIFACTS/_generation/`
**Audience:** Quality assurance, validation
**Purpose:** Test data, fixtures, test results

| Type | Examples |
|------|----------|
| Test data | Seed data, fixtures, mock data |
| Test reports | Coverage reports, test results |
| Validation | Integration test results, E2E test logs |

**Sponsor Interaction:** Test reports as proof of quality

---

### 8. Generated Assets
**Location:** `/SOURCE/[workspace]/build/`, `/SOURCE/[workspace]/dist/`
**Audience:** Deployment systems
**Purpose:** Compiled builds, bundles, deployment packages

**Sponsor Interaction:** Deployed application (production environment)

---

### 9. Runtime Logs
**Location:** `ARTIFACTS/activity-log.txt`, `/logs/`
**Audience:** Project management, debugging
**Purpose:** Activity tracking, execution logs, metrics

| Type | Storage |
|------|---------|
| Activity log | Append-only text file (`ARTIFACTS/activity-log.txt`), queried via `activity-log-file` MCP server |
| Execution logs | Console output, log files |
| Metrics | Performance data, usage analytics |

**Sponsor Interaction:** Progress dashboards, status reports

---

## Sponsor Communication Guide

### Documents Sponsor Should Review

| Category | Documents | When |
|----------|-----------|------|
| User Input | PRDs, BRDs | Project start (they provide) |
| App Specs | `requirements-matrix.yaml`, `data-dictionary.yaml`, `api-design.md`, `system-architecture.md`, `tech-stack.md` | Phase gates (P2→P3, P3→P4) |
| Test Reports | Coverage, validation results | P5 completion |

### Documents Sponsor Receives (Summary Only)

| Category | Documents | When |
|----------|-----------|------|
| Working Docs | Phase handovers, actionlist | Progress updates |
| Runtime Logs | Activity summaries, blocker reports | Weekly status |

### Documents Sponsor Does Not See

| Category | Reason |
|----------|--------|
| Framework Documents | Internal governance |
| App Configuration | Technical implementation detail |
| Implementation Code | Technical implementation detail (see working app instead) |
| Generated Assets | Deployment artifacts |
