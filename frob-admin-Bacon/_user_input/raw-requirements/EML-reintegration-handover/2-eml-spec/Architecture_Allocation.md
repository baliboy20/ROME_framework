## 1. Layers & devices
| Layer | Technology | Runs on (devices) | Notes |
|---|---|---|---|
| Frontend | Web admin module (browser-based) — current build scope only (DR-6). Claude agent interface (chat client) — deferred, not built this pass | Desktop/mobile browser (Owner) | Both are thin clients; neither performs business-rule enforcement (DR-6) |
| Middle/services | Cloudflare Workers API | Cloudflare edge network | Owns all business-rule enforcement/validation (DR-6) — e.g. BR-06's ≥24hr/<24hr refund computation, template `active`-per-use-case uniqueness, empty-reply/missing-Explanation-Block blocks. Also the send-dispatch path (REQ-EML01/02/05/06/07/08/09), matching the inherited FOB pattern's `core-notifications` send path — dispatch resolves each send's recipient set (Party Leader + every opted-in `co_leaders` row for the Booking, F-18) at send time, not via a stored per-recipient row. Cloudflare Email Routing (inbound capture, REQ-EML11) is a separate, presumed edge mechanism that hands off to this same Workers layer for persistence/threading/forwarding logic |
| Data | Cloudflare D1 (matching inherited FOB convention) | Cloudflare edge network | Durable storage for `email_templates`, `sent_emails`, `explanation_blocks`, `received_emails`, `email_threads`, `co_leaders` (Data_Dictionary.md §2, `co_leaders` added v0.5 per DR-11). `bookings`/`departures` are read-only references into the external `booking` module's own D1 tables, never written by EML |

## 3. Mechanisms (referenced, non-normative)
- Cancellation-request classification (REQ-EML03/04) reuses the ≥24hr/<24hr cutoff logic first stated in BR-06/DR-3's discussion — a single computation, not duplicated per REQ.
- The presumed `core-notifications` subsystem (inherited FOB project) is assumed to own actual message delivery/bounce/complaint tracking (`sent_emails.status` transitions beyond queued→sent, per `DOMAIN-LEXICON.md` §5) — this allocation table does not re-specify that mechanism, consistent with Module_Map.md's `presumes`.
- **Categorisation cascade (REQ-EML11)** — a Workers-layer rule sequence run in strict order, first match wins: (1) reply-reference threading, (2) thread inheritance from an existing link, (3) reference-number extraction from subject/body, (4) unambiguous sender-address lookup, (5) `unlinked`/`ambiguous` fallback. Deliberately implemented as data-driven, ordered rules (not hardcoded branching) so the sequence can be rearranged/extended without changing REQ-EML11's contract — sponsor ruling 2026-07-23. This mechanism is shared by REQ-EML11 (automatic) and read by REQ-EML14 (manual override of its outcome).

## 4. Presumed shared subsystems — who provides each `presumes` entry
| `presumes` entry (Module_Map.md §1) | Provider | Notes |
|---|---|---|
| `core-notifications` | Inherited FOB project (external) | Owns provider-level send/delivery/bounce/complaint tracking beyond EML's queued→sent dispatch |
| Cloudflare Workers API layer | This project, built as part of EML's own middle/services layer (§1 above) | Not an external presumption in the same sense as `core-notifications` — it's EML's own middle layer, named as `presumes` in Module_Map.md because the *web admin module* and *Claude agent interface* (frontend layer) presume it exists as their backing service, per DR-6 |
| Cloudflare Email Routing | Cloudflare platform (edge mechanism, external to this project's own code) | Inbound capture mechanism for REQ-EML11 — a platform feature, not built by EML; EML's Workers layer is the destination worker it hands off to |
