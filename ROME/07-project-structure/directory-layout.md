# ROME Project Directory Structure

**Version:** 5.0
**Date:** 2025-11-06
**Purpose:** Standard directory layout for ROME projects

---

## Overview

ROME v5.0 uses a clear separation between **user input** and **generated artifacts**.

---

## Standard Structure

```
PROJECT/
├── user_docs/              ← USER INPUT (you place files here)
│   ├── original-prd.pdf    ← Your original PRD/BRD
│   ├── business-case.docx  ← Any supporting docs
│   ├── mockups/            ← Any existing designs
│   └── notes.md            ← Your project notes
│
├── requirements/           ← TALIB OUTPUT (HTM artifacts)
│   ├── requirements-matrix.yaml
│   ├── data-dictionary.yaml
│   ├── component-registry.yaml
│   ├── htm-ready-prd.md    ← Transformed PRD (if needed)
│   └── docs/
│       └── features/       ← Feature documentation
│
├── dev/                    ← PMA OUTPUT (architecture specs)
│   ├── architecture_specification.md
│   ├── data_model.md
│   ├── actionlist.md       ← Task assignments
│   ├── use_cases.md
│   └── activity_status.txt
│
└── design/                 ← CLARA OUTPUT (UX specs)
    ├── design_system.md
    ├── component_specs.md
    ├── prototype_ui.md
    └── wireframes/
```

## Directory Purposes

### `user_docs/` - Your Original Documents

**Purpose:** Store all original user-provided documentation

**Who uses it:**
- You (the user) place files here
- Talib (HTM) reads from here

**What goes here:**
- Original PRD (Product Requirements Document)
- BRD (Business Requirements Document)
- Any specifications you received
- Supporting documents
- Reference materials
- Your notes and ideas

**File formats:** Any format (PDF, Word, Markdown, slides, etc.)

**Example:**
```
user_docs/
├── crm-requirements-v1.pdf
├── stakeholder-interviews.docx
├── competitor-analysis.md
└── ui-inspiration/
    ├── screenshot1.png
    └── screenshot2.png
```

**Critical:** This is the **entry point** for ROME. Start here.

---

### `requirements/` - HTM Generated Artifacts

**Purpose:** Structured requirements output from Talib (Phase 1)

**Who creates it:** Talib (HTM Decomposer robot)

**Who reads it:**
- PMA (Phase 2)
- Clara (Phase 2A)
- Chaperone (Phase 2B)
- All development robots (Phase 3)

**What's inside:**
- `requirements-matrix.yaml` - Epic → Feature → Story → Task hierarchy
- `data-dictionary.yaml` - All entities, attributes, relationships
- `component-registry.yaml` - Technical components mapping
- `htm-ready-prd.md` - Transformed PRD (if original wasn't HTM-ready)
- `docs/features/FEAT-XXX.X.md` - Detailed feature documentation

**DO NOT manually edit these files** - they're generated by Talib

---

### `dev/` - Architecture Specifications

**Purpose:** Technical architecture and planning from PMA (Phase 2)

**Who creates it:** PMA (Project Manager/Architect robot)

**Who reads it:**
- Clara (for tech constraints in UX)
- Chaperone (for validation)
- Development robots (for implementation)

**What's inside:**
- `architecture_specification.md` - Tech stack, patterns, API design
- `data_model.md` - Database schema design
- `actionlist.md` - Task breakdown for all robots
- `use_cases.md` - User scenarios and flows
- `activity_status.txt` - Current phase status

---

### `design/` - UX Specifications

**Purpose:** User experience design from Clara (Phase 2A)

**Who creates it:** Clara (UX Designer robot)

**Who reads it:**
- Charlie (Frontend Developer) - primary consumer
- PMA (for architecture validation)
- Chaperone (for completeness check)

**What's inside:**
- `design_system.md` - Colors, typography, spacing standards
- `component_specs.md` - UI component specifications
- `prototype_ui.md` - Main UX specification document
- `wireframes/` - Screen layouts and flows
- `user_flows.md` - Interaction patterns (optional)

**Critical:** Charlie MUST use these exact specs (pixel-perfect implementation)

## Workflow by Phase

### Phase 1: HTM Requirements (Talib)

**Input:**
- `user_docs/*` (your PRD/BRD)

**Output:**
- `requirements/*.yaml` (3 YAML files)
- `requirements/docs/features/*.md` (feature docs)

**Command:**
```bash
cd robot_talib
claude
# Tell Talib: "Please read PROJECT/user_docs/my-prd.pdf"
```

---

### Phase 2: Architecture (PMA)

**Input:**
- `requirements/*.yaml` (from Talib)

**Output:**
- `dev/*.md` (architecture specs)
- `dev/actionlist.md` (task assignments)

**Command:**
```bash
cd robot_pma
claude
# Tell PMA: "Phase 1 complete, please validate and begin architecture"
```

---

### Phase 2A: UX Design (Clara)

**Input:**
- `requirements/*.yaml` (from Talib)
- `dev/architecture_specification.md` (from PMA)

**Output:**
- `design/*.md` (UX specs)
- `design/wireframes/*.md` (layouts)

**Command:**
```bash
cd robot_clara
claude
# Tell Clara: "Please create UX specifications"
```

---

### Phase 2B: Validation (Chaperone)

**Input:**
- `requirements/*.yaml` (from Talib)
- `dev/*.md` (from PMA)
- `design/*.md` (from Clara)

**Output:**
- Validation report
- Issues identified

**Command:**
```bash
cd robot_chaperone
claude
# Tell Chaperone: "Please validate all Phase 1-2 artifacts"
```

## Best Practices

### 1. Never Mix Input and Output

❌ **Wrong:**
```
requirements/
├── my-prd.pdf              ← User input
├── requirements-matrix.yaml ← Generated output
```

✅ **Correct:**
```
user_docs/
└── my-prd.pdf              ← User input

requirements/
└── requirements-matrix.yaml ← Generated output
```

### 2. Keep Original Documents Intact

- Never edit files in `user_docs/` during ROME workflow
- If PRD changes, version it: `prd-v1.pdf`, `prd-v2.pdf`
- Generated artifacts will be recreated if you rerun phases

### 3. Trust the Structure

- Robots know where to find their inputs
- Don't move files around
- Don't rename generated files
- Follow the standard layout

### 4. Use Descriptive Names

**User docs:**
```
user_docs/
├── crm-requirements-2025.pdf    ✅ Clear
├── stakeholder-feedback.docx    ✅ Clear
└── doc1.pdf                      ❌ Unclear
```

## Common Questions

**Q: Where do I put my PRD?**
A: `PROJECT/user_docs/original-prd.pdf` (or any filename you prefer)

**Q: Can I have multiple PRDs?**
A: Yes! Put them all in `user_docs/` and tell Talib which ones to read

**Q: What if I don't have a formal PRD?**
A: That's fine! Create `user_docs/project-notes.md` and describe your idea there

**Q: Can I delete user_docs/ after Phase 1?**
A: No! Keep it for reference and future iterations

**Q: What if I need to update requirements?**
A: Add updated docs to `user_docs/`, rerun Talib, and iterate

**Q: Where does actual code go?**
A: In the project root or in a `src/` directory (outside PROJECT/ structure)

## Setup Commands

### Manual Setup

```bash
# Create project structure
mkdir -p MyProject/user_docs
mkdir -p MyProject/requirements
mkdir -p MyProject/dev
mkdir -p MyProject/design

# Place your PRD
cp ~/Documents/my-prd.pdf MyProject/user_docs/

# Create symlink for easy access
ln -s MyProject Project
```

### Automated Setup

```bash
# Use ROME workspace script
./ROME/scripts/setup-workspace.sh
# Enter project name when prompted
# Structure created automatically
```
