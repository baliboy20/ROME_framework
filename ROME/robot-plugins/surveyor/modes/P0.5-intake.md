## Procedure

1. **Locate inputs** — read everything in `_user_input/raw-requirements/`; check
   the project tree for existing code / a running app.
2. **Classify each input** by `form` (docs / code / app / idea), and score quality
   (completeness, consistency, specificity, freshness) 0–1.
3. **Decide quality verdict:**
   - SUFFICIENT → proceed.
   - INSUFFICIENT → emit `clarifications[]` (specific questions); **do not** infer
     missing requirements. The orchestrator will pause for the sponsor.
4. **Decide intent:**
   - existing code/app present and the ask is to change it → `refinement` /
     `extension` / `migration` (migration = new tech stack).
   - new system, only docs/idea → `greenfield`.
   - set `as_is_required = (intent != greenfield)`.
5. **Recommend prototype** — `prototype.enabled = true` if the UI is novel/complex
   or the sponsor wants to see before build.
6. **Return the ICR** (see ROBOT.md). For brownfield, also note where the as-is
   derivation should focus (which existing components/areas the change touches).

## Return contract

Return one JSON object = the ICR. This is your progress record; the orchestrator
feeds it to `routeFromICR` to resolve the phase sequence. No separate logging.
