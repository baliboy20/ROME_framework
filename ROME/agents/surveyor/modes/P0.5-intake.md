## Procedure

1. **Locate inputs** — read everything in `_user_input/raw-requirements/`; check
   the project tree for existing code / a running app.
2. **Classify each input** by `form` (docs / code / app / idea / **spec** — a
   technical specification carrying TDRs), and score quality (completeness,
   consistency, specificity, freshness) 0–1.
3. **Read reliability markers (PROP-047).** For each input, read any
   `**Status:**` marker (`Reliable` / `PROPOSED` / `RECONSTRUCTED` /
   `UNDEFINED`) into `reliability`; assess it yourself where absent. Shaky
   inputs need `sponsorAuthorized: true` to route (ROME-AX-18) — surface, never
   silently proceed.
4. **Extract TDRs from spec inputs (PROP-052).** From `decisions.tdr.yaml`
   directly, or from a markdown TDR table (emit the canonical YAML and obtain
   the sponsor's one-time extraction confirmation — the confirmation grants
   authority). Apply the carrier-reliability downgrade (ROME-AX-30): in a
   non-Reliable carrier every APPROVED TDR becomes PROPOSED. Flag
   decision-shaped prose outside a TDR as an unconstituted candidate in that
   input's `issues[]` (report, not block). Return the result in `tdrs[]`.
5. **Ask the infra-constraint block (PROP-051 §2.4)** — one pass, up front:
   existing hosting/deployment accounts; existing vendor accounts
   (payment/email/storage/auth/analytics); stacks the sponsor's team operates;
   vendors/technologies to avoid; local-dev expectations. Record in
   `infraConstraints` (absence of constraints is a valid answer).
6. **Decide quality verdict:**
   - SUFFICIENT → proceed.
   - INSUFFICIENT → emit `clarifications[]` (specific questions); **do not** infer
     missing requirements. The orchestrator will pause for the sponsor.
7. **Decide intent:**
   - existing code/app present and the ask is to change it → `refinement` /
     `extension` / `migration` (migration = new tech stack).
   - new system, only docs/idea → `greenfield`.
   - set `as_is_required = (intent != greenfield)`.
8. **Recommend prototype** — `prototype.enabled = true` if the UI is novel/complex
   or the sponsor wants to see before build (default-on for UI signals, PROP-037).
9. **Return the ICR** (field table in ROBOT.md). For brownfield, also note where
   the as-is derivation should focus (which existing components/areas the change
   touches).

## Return contract

Return one JSON object = the ICR. This is your progress record; the orchestrator
finalizes it deterministically (`guard-cli intake` → `routeFromICR` +
`finalizeIntake`, persisting `tdrs`/`infraConstraints` into state). No separate
logging.
